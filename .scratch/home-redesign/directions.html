Why the current home page reads as vibecoded

It isn't one problem. The page stacks almost every pattern that AI-generated landing pages share, so even good content reads as a template. Everything below is in app/page.tsx and app/globals.css.

The fix isn't a new coat of paint. Each direction below drops the landing-page skeleton entirely and picks one idea that only kubesim could have. They share four rules: one typeface family plus one mono, one accent colour used only for meaning, no decoration that isn't information, and copy written as plain statements.

All text, counts and terminal output in the mockups are real: 19 lessons in 7 tracks, 30 challenges, 2 practice exams, 11 explainers, and output produced by the engine with seed: 42.

A · Manual page

The site reads like man kubesim. One monospace font, black on white, no images.

The idea

People come here to learn a CLI. Treat the home page as the tool's documentation: NAME, SYNOPSIS, DESCRIPTION, then the curriculum as a plain table. The only "visual" is a real terminal with a real prompt, so the first thing a visitor can do is type.

What goes away

  • Every illustration, gradient, card, shadow and rounded corner
  • The serif display font
  • The isometric hero (the real Cluster View is one click away)

Spec

TypeIBM Plex Mono only, 14.5 / 1.6. One size for body, one for the opening line.
Colourpaper ink errors only
LinksUnderlined; inverted block on hover, like a terminal selection
Build costLowest. Mostly deleting code.

Risks

  • Cold for absolute beginners who've never seen a terminal.
  • Hides the visual Cluster View, the thing that makes kubesim different from a doc site.

C · Control room

The home page is a running cluster. Marketing is one sentence above it.

The idea

Today the best thing on the page, the live cluster, sits below a drawing of itself. Flip it: the first screen is the actual app (Cluster View, terminal, event stream) with a single line of explanation and suggested commands. The site's navigation becomes the app's left rail. Below the fold is a dense index of everything to do, laid out like a tool's file list rather than marketing cards.

The event stream does the teaching: each event can carry a one-line "why" in plain English, which is the thing kubesim does that a real cluster doesn't.

What goes away

  • The hero, the isometric illustration and the stats
  • All section headlines and eyebrows
  • The fidelity section (its claim is proven by the screen itself; keep one line and a link)

Spec

TypeGeist + Geist Mono (already loaded; the fonts weren't the problem)
Colourcanvas ink status only, matching the Cluster View's tokens
Shape6 px radius max, 1 px borders, no shadows
Build costMedium-high. Reuses TryIt, Cluster View and the terminal; needs a server-rendered static first frame so the page isn't blank before JS.

Risks

  • Performance: the engine boots above the fold. Ship the SSR'd snapshot first, start the clock on first interaction.
  • Mobile: three panes don't fit. On phones, show the terminal and a compact node list; the Cluster View goes behind a tab.
  • First-time visitors need the one-line explanation to be very clear.

What happens when you delete a Pod.

Try it yourself — lesson 1Open an empty cluster
1
kubectl sends a DELETE to the API server, which marks the Pod for deletion in etcd.
2
The kubelet on worker-2 sees it, stops the container, and the Pod is gone.
3
The ReplicaSet controller counts 2 Pods but wants 3, so it creates a new one with no Node yet.
4
The scheduler scores the Nodes and binds the new Pod to worker-1, which had more room.
5
The kubelet on worker-1 starts the container. kubectl get pods shows it with AGE 4s.

Recommendation: C, with A's restraint below the fold

Go with C (Control room). kubesim's one advantage over every Kubernetes tutorial is that the cluster is real enough to touch, and it's free. C is the only direction where that's the first thing anyone sees, and you already have TryIt, the Cluster View and the terminal, so it's mostly rearranging rather than drawing. It also can't be mistaken for a template, because a template doesn't contain a working cluster.

Keep everything under the first screen as plain as A: tables and lists, no cards, no section slogans.

Steal from the others

  • From D: the annotated five-step drawing is excellent explainer material. Use it as the header of the "How self-healing works" explainer, or as the static fallback for C on mobile.
  • From B: the margin-note way of stating fidelity ("Back-off doubles from 10 s to a 5-minute cap, the kubelet's real defaults") is more convincing than a "Modelled on v1.37" section. Put those lines in C's event "why" annotations.
  • From A: link style and copy voice. Say what a thing is, in one sentence.

Rules for whichever you choose

  1. No eyebrow labels. If a heading needs a label to make sense, rewrite the heading.
  2. One accent colour, and it means something (status, or a link). No decorative gradients, blobs, grain or glow.
  3. No fake chrome: no traffic-light dots, no pulsing dots that don't reflect real state.
  4. No cards for navigation. Use lists and tables; they hold more and read faster.
  5. Copy is plain statements. No "This isn't a video", no rule-of-three slogans, no italic accent word.
  6. One primary action per screen.

Rough plan for C

  1. Server-render a static snapshot of the seeded cluster (nodes, pods, last few events, terminal scrollback) so the first paint is the cluster with no JS.
  2. Hydrate TryIt into that layout; start the clock on first interaction or after it's visible for a second.
  3. Add an optional one-line why to events the engine emits (SuccessfulCreate, Scheduled, BackOff, Killing, FailedScheduling). This is also useful inside lessons.
  4. Replace the bento, fidelity and closing sections with the three-column index.
  5. Mobile: terminal plus a compact node/pod list; Cluster View behind a tab.
  6. Remove .bg-field, HeroCluster, Eyebrow and Arrow once nothing uses them.
